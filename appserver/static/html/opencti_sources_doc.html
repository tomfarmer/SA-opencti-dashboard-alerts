OpenCTI Correlations Configuration

This page lets you define basic OpenCTI correlations for URL, Hash, Domain, IP, and Email indicators. Each row describes one correlation: an IOC type, a set of indexes to monitor, and the fields in those indexes that contain candidate values. The OpenCTI threat-match engine reads these definitions and runs its saved searches every five minutes over the last five minutes of indexed data, writing normalized matches into the opencti_alerts summary index.

How it works

  • The table lists existing correlations with columns for Enable, Name, Description, Index List, Field List, Last run, and Actions.
  • Each row represents one correlation configuration for a given IOC type (URL, Hash, Domain, IP, or Email).
  • The Enable toggle marks a correlation as active; the engine will only honor enabled rows.
  • The Index List and Field List values are stored in a KV collection and are used by macros to build the SPL query.
  • The Last run column is informational; the underlying threat-match saved searches are scheduled to run every five minutes over the last five minutes of indexed data.

Creating and editing correlations

  • Click Add Basic Correlation to open the modal form.
  • Provide a unique Name and optional Description.
  • Select an IOC Type (URL, Hash, Domain, IP, or Email).
  • Enter a comma-separated List of Fields that contain the indicator values in your events (no spaces between commas).
  • Enter a comma-separated List of Indexes to search (no wildcards like index=*, no spaces between commas).
  • Click Create to save; the correlation appears in the table and will be honored by the threat-match saved searches.
  • Use the row Edit action to reopen the modal with existing values and update fields/indexes as needed.

Best practices

  • Think in terms of “one correlation per index per IOC family” where possible.
  • Use indexes that contain normalized, high-signal telemetry; noisy or duplicate sources will inflate hit counts.
  • After changing source indexes, allow a couple of matcher runs to populate the opencti_alerts summary index.
  • Avoid scanning the same heavy index multiple times with slightly different SPL every five minutes; rescanning is what costs the most.

Good vs bad patterns

The goal is to minimize how often the same index is scanned by the 5-minute threat-match searches. It is better to have one correlation that covers all relevant fields in an index than several correlations that all hit the same index with small variations.

Bad (too many passes over the same index)

ip – Zeek conn (src)          → index=zeek_conn fields=id.orig_h
ip – Zeek conn (dst)          → index=zeek_conn fields=id.resp_h
ip – Zeek conn (internal)     → index=zeek_conn fields=id.orig_h,id.resp_h with some internal filter
ip – Zeek uncommon ports      → index=zeek_conn with different SPL filters

Now 4 out of 4 correlations all hit the same heavy index: zeek_conn.

Good (each index has its own correlation)

Domains

domain – Zeek DNS             → index=zeek_dns fields=query
domain – Proxy / Web filter   → index=proxy_logs fields=host,domain

IPs

ip – Zeek conn                → index=zeek_conn fields=id.orig_h,id.resp_h
ip – Firewall perimeter       → index=firewall_main fields=src_ip,dst_ip
ip – EDR network telemetry    → index=edr fields=remote_ip
ip – Velociraptor artifacts   → index=velociraptor fields=dest_ip

Hashes (useful for your image pipeline)

hash – AV scan results        → index=image_pipeline_av fields=file_hash,sha256,md5
hash – YARA hits              → index=image_pipeline_yara fields=hash,sha256
hash – Velociraptor hashes    → index=velociraptor fields=hash
hash – EDR collected binaries → index=edr fields=file_hash

URLs

url – Zeek HTTP               → index=zeek_http fields=uri,host
url – Proxy logs              → index=proxy_logs fields=url
url – Image pipeline scraping → index=image_pipeline_strings fields=extracted_url

Emails

email – SMTP logs             → index=smtp_logs fields=sender,recipient
email – O365 message trace    → index=o365_email fields=sender_address,recipient_address

Email section

For Email correlations, choose indexes that contain SMTP-style events and specify fields that carry sender/recipient addresses (for example from, to, mailfrom, rcptto). The correlation logic normalizes and validates these fields before matching against the OpenCTI email IOC lookups.

Troubleshooting

  • If you see errors when creating or editing a correlation, ensure your Splunk role can read and write KV store data for this app.
  • If threat-match dashboards show no hits, confirm that your source indexes and fields actually contain the expected indicators for the time window.
  • If you suspect performance issues, look for correlations that repeatedly scan the same heavy index and consolidate them where possible.
